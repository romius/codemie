## Cross-repository consistency (codemie ↔ codemie-ui)

- **The frontend beacon URL almost certainly has a duplicated `/v1` and will 404 in production — and the new test asserts the broken URL as correct.** `useAuthCallbackListener.ts` builds `` `${api.BASE_URL}/v1/mcp-auth/oauth2/callback-diagnostics` ``, and `useAuthCallbackListener.test.tsx` asserts `expect(url).toBe('https://api.example.com/v1/v1/mcp-auth/oauth2/callback-diagnostics')`. The doubled segment means `api.BASE_URL` already ends in `/v1`. Because the whole call is fire-and-forget with every failure swallowed, a 404 is completely invisible: the backend `timeout` branch, its WARNING, its test, and the two new pydantic fields would all be dead code in production, and nobody would notice. This is the single highest-value item to verify.
- **`sendBeacon` with a `Blob` of type `application/json` is not a CORS-safelisted content type, so a cross-origin beacon requires a preflight the Beacon API cannot satisfy in the unload path.** `useAuthCallbackListener.ts` new `reportCallbackTimeoutDiagnostics`. Given `api.BASE_URL` is a different origin from the app (per the test fixture `https://api.example.com`), this beacon may be silently dropped by the browser unless the backend's CORS config explicitly preflights this route. Nothing in the backend diff touches CORS. `text/plain` is the usual workaround; the backend would then need to accept it.
- **The `sendBeacon` return value is ignored, so there is no fallback when the browser refuses to queue.** Same hunk: `navigator.sendBeacon(url, ...)` then unconditional `return`. `sendBeacon` returns `false` when the payload exceeds the user agent's queue quota. The `fetch(..., {keepalive:true})` branch below is reachable only when `sendBeacon` is entirely absent, and it is never exercised by any of the four new tests.
- **The timeout diagnostic carries no state prefix, so it cannot be joined to the initiate log line the rest of this change exists to create.** The frontend posts only `auth_config_id`; the backend timeout WARNING (`_diagnostics.py`) logs `auth_config_id`, `waited_ms`, `phase`, `opener_present`, `target_origin`. The stated goal (AC5, per the test docstrings) is joining initiate ↔ callback by state prefix, and the timeout case — the one where no callback ever arrived and correlation matters most — is the one case that lacks the join key. For discovered flows `auth_config_id` may also be a synthetic id, weakening the join further.
- **Deployment ordering is unhandled.** If the UI ships before the backend, `result: "timeout"` fails the `Literal["success","error","timeout"]` validation with a 422 and the beacon is silently lost (no retry, no fallback). Conversely `waited_ms` has a backend ceiling of `le=3_600_000` that the frontend never checks: the UI sends `getAuthCallbackTimeoutSeconds() * 1000`, so an operator configuring a timeout above 3600s silently 422s every beacon. The `le` bound and the UI's timeout config are coupled but that coupling is documented nowhere (the adjacent comment only mentions "keep the UI timeout <= the backend PKCE lifetime").

## Misleading / low-value telemetry

- **`opener_present` and `phase` are hardcoded literals on the frontend, but read as observations on the backend.** `useAuthCallbackListener.ts` always sends `opener_present: false` and `phase: 'awaiting_callback'`. In the *other* diagnostics branch `opener_present=false` is a genuine failure signal ("we lost `window.opener`"); in the timeout WARNING it is a constant that means nothing. Anyone triaging will read a real signal into a stub value. `phase` likewise has exactly one possible value while being typed as a 64-char free string.
- **`waited_ms` reports the configured timeout, not the measured elapsed time.** `reportCallbackTimeoutDiagnostics(authConfigId, resolvedTimeoutMs)` passes the constant. The field name promises a measurement. A backgrounded tab whose timer fires late, or a timer that fired early, is indistinguishable — which is precisely the class of bug a "how long did the client actually wait" field should expose.
- **The SAML flow logs `"MCP OAuth2 initiate issued: flow=saml"` and labels the `RelayState` as `state=`.** `_initiate.py` `@@ -345,6 +413,18 @@`. SAML is not OAuth2; a log search for "MCP OAuth2 initiate" will now return SAML flows, and a search for OAuth2 problems will surface SAML noise. It also emits `client_id=None redirect_uri=None resource=None scope=None` on every single SAML initiate because `_describe_authorize_request` is OAuth2-shaped — four dead fields per line, and the new test `test_saml_initiate_logs_info_with_state_prefix_and_authorize_fields` asserts each of them, cementing the noise.
- **No length bound on the logged authorize-request fields.** `_sanitize_log_value` neutralizes control characters but does not truncate. `scope`, `resource` and `redirect_uri` for a discovered flow originate from remote AS metadata; an oversized `scope` inflates every INFO line for that server. The pydantic model in `_diagnostics.py` uses `max_length` for exactly this reason; `_common.py` does not.
- **`user_id` is now written into INFO lines in four initiate paths and the discovery resolution path.** Worth a deliberate decision rather than an incidental one, given log retention/PII policy — the diff adds it without comment.

## Tests

- **`test_callback_entry_log_state_prefix_joins_to_initiate` is tautological.** `test_oauth2_callback_bridge.py`, new block. It patches `shared_logger.info` *after* the initiate call, so the initiate log line is never captured; it then asserts the callback line contains `_log_state_prefix(known_state)` — i.e. it compares the helper against itself on a state it chose. It proves nothing about the two lines being joinable, which is exactly what its docstring claims it proves. The initiate call and its `assert initiate_response.auth_url == auth_url` are ceremony around a stub.
- **The state fixtures are `"j"*40`, `"e"*40`, `"s"*40`, `"d"*40`, `"r"*40`, `"y"*40` — single repeated characters.** Every one of these makes `state[:12]` a run of the same character, so no test can detect the practical failure mode: if the real state is a structured/signed token with a constant header, the first 12 characters may be *identical across all users and all flows*, making the join key useless. A realistic base64 signed-state fixture is needed to validate that 12 characters actually discriminate.
- **`test_describe_authorize_request_returns_all_none_on_malformed_url` does not exercise the error path it is named for.** `urlsplit("not a url::")` does not raise; it returns empty netloc and empty query, so all fields become `None` through the `or None` / `.get()` happy path. The test passes for the wrong reason and would keep passing if the `try/except` were deleted.
- **All four new frontend tests call `vi.unstubAllGlobals()` as the last statement of the test body rather than in an `afterEach`.** `useAuthCallbackListener.test.tsx`. If any assertion in the body fails, the `navigator` stub leaks into every subsequent test in the file. The first test additionally calls `vi.useRealTimers()` mid-body and never restores fake timers, so unless a `beforeEach` re-establishes them, timer mode leaks too.
- **`test_build_saml_initiate_passes_mcp_config_id_as_required_param` asserts `pytest.raises(TypeError)` for a missing keyword argument.** That tests CPython's argument binding, not this system's behavior, and it will have to be deleted the moment anyone gives the parameter a default. It also documents the breaking-signature risk noted above without addressing it.
- **`test_callback_diagnostics_timeout_result_logs_distinct_warning_message` funnels both `logger.warning` and `logger.info` into one list named `warned`.** The `len(warned) == 1` assertion is doing double duty (a warning fired; no info fired) in a way that will read as a bug to the next maintainer, and a future INFO added to the timeout path will fail this test with a confusing message.
- **No test covers the un-guarded `urlsplit(response.auth_url)` in `_initiate.py`** (the 500 described above), **the `fetch` keepalive fallback** in the frontend, **`sendBeacon` returning `false`**, or **a `state` containing CR/LF reaching the callback entry log**. Each is a path the diff newly created.

## Minor

- `parse_qsl` is called with default `keep_blank_values=False`, so `state=` (empty) is dropped and logs as `state=None`, indistinguishable from "no state parameter at all". Same for `scope=`.
- `parse_qsl` decodes `+` to a space, so a scope logs as `openid profile` rather than the wire value `openid+profile` (asserted as correct in three tests). Harmless for scopes, lossy if any of these fields ever legitimately contains a literal `+`.
- `urlsplit` + `parse_qsl` is executed twice per initiate — once for the state, once inside `_describe_authorize_request` — and the identical three-line extraction block is copy-pasted into four functions. One helper returning `(state, fields)` removes both the duplication and the unguarded-call bug in a single change.
- `_diagnostics.py` now imports the private `_sanitize_log_value` from `_common`; any other module that imported it from `_diagnostics` (its previous home) breaks. Not visible in this diff — worth a grep.
- The `_diagnostics.build_oauth2_callback_diagnostics_response` docstring was updated for `timeout`, but the early `return Response(status_code=204)` bypasses whatever the pre-existing branch returns; the diff does not show the tail of the function, so it is unverifiable from here whether the two branches agree on status code and body.
